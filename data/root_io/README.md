# ROOT-I/O dataset family

For experimental Qwen SFT using the 617-question bank, see
[the ROOT post-training pipeline](../../training/root_sft/README.md).
It preserves this source bank and generates separate balanced, grouped Parquet
splits; the student workbook and legacy split labels are not direct trainer inputs.

This family teaches an agent to inspect a ROOT file with bounded tools and
explain the observed contents in plain language. Initial tasks are read-only:

1. inventory ROOT objects;
2. inspect a tree and selected branches;
3. summarize one branch over a bounded event prefix; and
4. combine those observations into a concise file description.

ROOT modification, arbitrary expressions, histogram production, and event
selection are outside version `v0.1`.

## Authoring contract

Author one canonical source record using `schema/task.schema.json`. Store the
actual tool calls, tool results, and reference answer in `trajectory`; never
invent a ROOT inventory. A future shared renderer will convert that canonical
episode into Codex and OpenCode records.

Each source record must identify its fixture with a relative path, SHA-256,
and immutable dataset revision. Use `dataset_family: "root_io"`. Assign the
train, validation, or test split before harness rendering. Files or physics
samples that are near-duplicates must stay in the same split.

`examples/inspect-diphoton.example.json` demonstrates the source shape using
the generated software-test fixture. Its zero SHA-256 is an explicit
placeholder, so the record is not publishable training data. Generate a file,
record its printed digest, replay every tool call, and replace the placeholder
before turning an example into a reviewed record.

Validate draft or reviewed JSON/JSONL records with:

```bash
python3 data/root_io/validate_tasks.py data/root_io/examples/*.json
```

Besides JSON Schema, this checks tool allowlists, call/result IDs, the final
reference answer, and the ban on placeholder checksums for reviewed records.

## Fixture policy

Do not commit large ROOT files. Publish reviewed fixtures to the project
Hugging Face dataset and pin an immutable revision and SHA-256 in each source
record. Tiny synthetic fixtures generated by `root_io/fixtures.py` are only
for tool tests and schema examples. Authentic training and evaluation records
should use reviewed ATLAS Open Data.

## Knowledge-question pilot

For the current **student self-study release**, use
[students/root_io](../../students/root_io/README.md). Its maintained source is
`question_bank/root_questions_617.jsonl`; rebuild and validate it with
`python students/root_io/build_release.py` from the repository root.
It has 182 topic-based core entries and 435 explicitly labeled practice variants.
The older generators below do not reproduce the editorial corrections in the 617 bank.
The strict training audit below can reject intentional student practice repetitions;
passing the student builder does not certify training splits or RL eligibility.

`question_bank/pilot.jsonl` contains 50 manually authored, source-grounded
questions for SFT. Rebuild and audit it with:

```bash
python3 data/root_io/build_knowledge_pilot.py
python3 data/root_io/audit_question_bank.py \
  data/root_io/question_bank/pilot.jsonl --expected-count 50
```

These records are deliberately `rl_eligible: false`: static reference answers
are supervised targets, not executable rewards. Promote only fixture-backed
tasks with replayed tool evidence to the operational schema used for RL.

Build and audit the expanded 500-question draft bank with:

```bash
python3 data/root_io/build_question_bank.py
python3 data/root_io/audit_question_bank.py \
  data/root_io/question_bank/root_questions_500.jsonl --expected-count 500
```

The expansion adds 30 HEP scenarios with 15 distinct ROOT-analysis decisions
per scenario. All related questions share a split group.

## Review checklist

- The fixture path is evaluator-local and relative to its allowed root.
- The SHA-256 and source revision reproduce the exact file.
- Every tool name appears in `tool_manifest.json`.
- Tool results were captured by executing the tool on that fixture.
- Required facts are supported directly by the captured results.
- Units or physics meanings are cited in provenance, not guessed from names.
- No close fixture or prompt variant crosses a dataset split.
- Codex and OpenCode renderings retain one `logical_task_id` and split.
